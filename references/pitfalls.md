# 实战踩坑清单

按发生频率排序。每一条都是真实翻过车的。

## 1. 预览系统给 HTML 注入 `data-page-node-id`

打开过的 HTML 会被注入这个属性，形如 `<div class="head" data-page-node-id="xxx">`。写正则批量改结构时：

- ❌ `<div class="head">(.*?)</div>` —— 一条都匹配不上
- ✅ `<div class="head"[^>]*>(.*?)</div>` —— 属性区一律用 `[^>]*`

## 2. 字符串计数平衡 ≠ 嵌套正确

用脚本改 HTML 后，`s.count('<div') == s.count('</div>')` 也可能布局全塌——因为嵌套错位（卡片提前闭合、img 露在卡外）。

**每次改完必须跑**：

```bash
python3 scripts/check_html.py 图.html
```

它会用 HTML 解析器报出未闭合的开标签、多余的闭合标签及其行号。本次实战中，两张卡的残骸就是这样被定位并重建的。

## 3. 批量正则误伤同类元素

按"任意 head + img"批量重排时，会把保障卡、底座卡一起改掉（本次误伤 14 处）。做法：先用**图片文件名前缀白名单**过滤，只改目标类别的卡；改完立即校验 div 平衡。

## 4. `<img>` 必须放在卡片 div 内部

放卡外时 `position: absolute` 相对页面定位，插画会飘到别处。批量插入后要检查 `<img class="illus"` 是否紧跟 `<div class="card..."` 之后、且在其闭合标签之前。

## 5. 胶囊标签压住插画

典型症状：标签 `padding-right` 留白不足，长标签换行后钻进插画区域。

正解不是调 padding 数值，而是**换结构**：把标题与插画放同一行的 `ptop`，标签在下方整行铺开——文字和插画天然分居左右，永不重叠。只有卡片太矮（<90px）时才用绝对定位 + padding 避让。

## 6. 插画太小 / 底部空白太多

用户会连续反馈这两个问题，本质是**行高与插画尺寸不匹配**。

- 插画 88–96px 时，卡片行高需 175–235px；
- 行高比实际需求高 20% 以上，底部就会空；
- 调整顺序：先定插画尺寸 → 算内容总高（插画 + 副标题 + 标签行数）→ 再排行高比例 → 截图看空白。

同一次调整里，某一层加高就必须压缩其他层，总高不变，否则整图超框。

## 7. 副标题位置反复

默认：副标题在标题**正下方**（左列内），不要放到插画下方，也不要和标题并排。用户说"恢复原位"时指的就是这个。

## 8. 描边太粗

2.5px 看着笨重，1.8px 与细线稿插画最协调；标签 chip 用 1.5px、层名竖条 5px，主次分明。

## 9. 生成图带水印 / 灰底

- 水印：图像编辑模型抹不掉，用 PIL 涂白或裁边；
- 灰底：`~235` 的米灰极常见，必须线性归一化，否则 `multiply` 后留灰斑。

## 10. 深色底图在浅色版式里崩

深色宣传图配黑底发光插画（`screen`），浅色卡片配纯白线稿插画（`multiply`）。混用必脏。若最终要浅色底，就不要先生成黑底插画再救——重抽更快。

## 11. 记事本式反复返工

改文案时只改 HTML 文本，不动 CSS；改版式时只动 CSS，不动结构。两类改动混在一次，出问题无法定位是谁的锅。

## 12. 为"凑空间"缩字号，破坏层级

症状：某一行卡片放不下标题，就把该行 `font-size` 调小一档（底座卡 15px、其他 16px）。用户一眼就能看出来："相同层级的字体大小为什么不一样"。

正解：**字号全图统一，放不下就折行**。`line-height:1.25` + `text-wrap:balance` + 去掉 `nowrap`；折行后仍显挤，就收插画宽度（8–12px）或加卡宽，绝不动字号。要压卡片高度只调 `padding`/`margin`。

## 13. 层徽章后缀 `<span>` vs `<small>`

七行徽章里有一行写成 `<span>大</span>`，其他行是 `<small>大</small>`——后缀继承了序号的大字号，"5 大"比"1 个"大一圈。等大卡 + 同构行最容易漏这种单处笔误，改完逐行比对标签结构。

```bash
grep -n "<span>个\|<span>类\|<span>大\|<span>项" 图.html   # 应为空
```

## 14. "插画高度统一"≠"插画尺寸统一"

只写 `height:68px; max-width:88px`，高度是齐了，但宽度随图比例自由变化：方图 68×68、2:1 横条 88×44，视觉大小差一倍，用户会说"插画尺寸应该是一致的"。

正解是统一**占位框**：`width:60px; height:60px; object-fit:contain`。代价是横长构图在框内显小，属固有特性，提前告知用户，别靠放大它们破坏统一。同时不要给某一行单写插画尺寸特例。

## 15. 梯形版式被滥用

等大卡 + 对称梯形要求"层数 ≥4 且卡片数单调递增、内容同构"。卡数不递增（3→5→4）时硬套，斜边会断成锯齿；内容量差异大时硬套，会出现某行卡内大片空白、另一行塞爆。

判断条件、几何算式、不满足时的替代方案见 `equal-card-trapezoid.md`。**默认版式仍是等宽网格铺满**。

## 16. 自行添加原图没有的内容（内容红线）

从思维导图/截图转架构图时，**只排原图已有的文字**。常见手痒行为全部禁止：给层加"1 个""5 大"计数徽章、右上角加"N 个 xx · N 个 xx"汇总副标、给卡补解释副标题、加"···更多"占位。用户原话："图片里不存在这些字样，不需要额外添加，没有要求的情况下，不要自己添加新的内容。"第一张图有数字是因为原导图本身叫 123456+N；没有数字语义的图，层徽章只放层名。

## 17. 行高必须按内容定，不能让 flex/grid 自动拉满

只有 4~5 层内容的图，若让行自动铺满画布，每行会被拉到 150~200px，卡内出现大片空白、插画占比掉到 40% 以下。正确做法：每行固定高度 = 内容实测高度（普通卡 ≈100、含两行胶囊的卡 ≈150–190、mini 卡 ≈85），行距 gap 22–30，`.layers` 用 `justify-content: center` 整体居中，剩余留白对称分布在页面上下——留白留给页面，不留给卡内。

## 18. 大卡片必须完整包住小卡片——不许靠肉眼，跑 check_fit.py

用户原话："大卡片要把小卡片包含进去，这个要沉淀下来，不要每次叠加。"这是反复被指出的问题：改层高、改列数、改 padding 后，最后一行分组块（.grp）掉到卡片边框外面或压住边框线，缩略截图上几乎看不出来，用户一放大就发现。

**正解是机器检查，不是眼力**：每次动过版式/层高/列数之后、export_png 之前，必跑：

```bash
python3 scripts/check_fit.py 图.html    # 退出码 0 = 全部包住
```

原理：Chrome headless 实测 getBoundingClientRect，比对每个 .grp/.chip 与父 .card 的 border box、卡片与层、scrollHeight 文字裁切、页面横向溢出。实测首跑就在"看起来没问题"的图上抓出 12 处越界（模型训练卡超出 22px、大数据 12px、区块链 9px）。

修法优先级：加高该层（按报的超出 px 加）→ 减小组卡 padding/gap → 让超长组 `.wide` 跨全行 → 减少列数。**禁止缩字号**（见第 12 条）。

## 19. 内边距不被吃 + 各层卡片左对齐——check_fit 已升级为机器检查（v22 起生效）

用户原话："卡片不要叠加，注意内间距和对齐，5层的第一张卡片没有左对齐。"两类肉眼难察觉的几何问题：

1. **小卡片侵入父卡片 padding 区**（EATS_CARD_PADDING）：层高被压缩后，内容把卡片底部 10px 内边距吃掉，小卡片贴着甚至压住边框线——border box 检查仍通过，但观感就是"两卡叠加"。check_fit 新增按 padding box 的检查（容差 1.5px）。
2. **各层卡片左右边缘没对齐**（CARD_LEFT/RIGHT_MISALIGN）：根因几乎都是**层名条宽度不统一**——某层有副标（.exp）`.lt` 就自动变宽（92→109px），把该层卡片整体推右 17px。修法：**`.lt` 用固定宽度**（取最宽层的实测值），不要 auto。注意：对称梯形版式各层行宽本来就不同，check_fit 已按"行宽方差>3px 即梯形"自动跳过对齐检查；等宽网格版式的对齐容差 3px。

连带经验：小卡片内「 · 」分隔的长词条列表，把「 · 」改成 `&nbsp;· `（nbsp 在前），配 `word-break: keep-all`，折行永远发生在分隔符后——行尾是「·」、行首是新词条目，不会出现词语被拆碎或「·」单独占一行。给 flow 组块加 `min-width` 挤压超长组的宽度反而会溢出，不要用。

## 20. PPT 字号必须落成整数磅，不许写会换算出小数的 px（2026-11-06）

DSL 的 px 写进 pptx 时 ×0.75=pt。写 7.3/10/13/29 这类 px 会落成 5.475/7.5/9.75/21.75 小数磅，用户在 PPT 里看到 6、7.5 直接返工。

**整数磅换算表（实测验证）**：10.67px→8pt / 12px→9pt / 16px→12pt / 17.33px→13pt / 28px→21pt。渲染器四舍五入到 0.01pt，上述值全部精确落整。

用户字号标准（按磅）：卡标题 10–12pt、组名 8–10pt、正文最小 8pt、层名 12–14pt。**先定磅值再反查 px，不要先随手写 px**。

## 21. 内容分隔符「·」在 PPT 里统一用「/」（2026-11-06）

用户指定。写 DSL 时词条间一律 ` / `，不要再写 ` · `。

## 22. 等宽 flex:1 分配是空白返工的根源——按内容宽度加权（2026-11-06）

用户连续两轮反馈"子卡片太高、空白很多"。根因：所有小卡 `flex: 1` 等宽硬分，长文字组放不下折行、短文字组大片留白，层高被迫撑高。

**做法**：同层小卡按正文像素宽度估算（全角×字号 + 半角×0.5字号 + 斜杠空格）分配 `flex: N`（如 4.5/3/2.2/0.9/4.4/2.4），层高按"组名行+正文行数"收紧。等高卡片按加权后仍然 stretch 等高。

**lint 卡在 bottom+5 加 flex 无效时**：说明该组正文本质放不下单行（内容长度 > 卡可用宽），别硬撑——转为允许两行并相应加层高，两行文字撑满同样没有空白。

## 23. slide 行删除脚本必须先备份+验 Box 计数（2026-11-06 实录）

按注释行删整块时，深度计数逻辑写错会把文件截断成 1 行，且同步副本一起污染。**铁律**：改 slide 前先 `cp` 备份到 /tmp；删除脚本执行后立即验证 `<Box` 与 `</Box>` 计数相等且 >0，再 upsert。
